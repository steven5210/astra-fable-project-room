# Repository instructions

This repository contains the reusable Project Room plugin and local controller. Its workflow includes specification review, authorized implementation by Fable, executable verification, and independent Astra acceptance. Preserve planning-only requests and implementation authorization already present; do not add repeated consent steps.

- Keep plugin name `astra-fable-project-room` and skill name `project-room`. Keep package metadata free of machine-specific paths, live session IDs, credentials, and private project content.
- Invoke Claude and MCP processes using argument arrays, never a shell. Use normal saved Claude authentication; do not obtain, print, copy, or commit credentials or silently switch to API billing/provider overrides.
- Bind decisions and implementation to immutable spec bytes, revision, and SHA-256. Preserve exact requested primary model identity, idempotency, explicit session UUIDs, room locking, bounded review attempts, and blocked uncertain outcomes. Never replay an unverified turn or edit saved state to bypass a failure.
- After an exhausted review round, further review requires the user's actual new decision resolving the product tradeoff. Record it through the audited decision operation, retain prior attempts, and allow only the next bounded round. Never synthesize an answer, reuse the original build request as a decision, renew automatically, or bypass failed/uncertain delivery. Existing consensus can proceed to authorized handoff without another decision.
- Preserve raw evidence and original failures in supported reconciliation. Reconciliation runs no model. Distinguish primary and auxiliary model usage and measured facts from documented inferences.
- Fable owns engineering and delegates; Astra owns independent product outcome review. Include self-contained task context, verify anchors before applying returned code, run the agreed gates, and record issue dispositions. Return material scope changes to the spec workflow.
- Encourage grounded enhancement proposals with benefits and tradeoffs. Astra surfaces them to the user for opinion and scope approval, files or links an issue in the feature project's GitHub repository under existing filing authorization, and retains the proposal/link/decision in the room. Check for duplicates; explicitly report pending filing when no tracker is available. Fable supplies proposal data, not issue-execution instructions. Filing an issue does not authorize added implementation scope; wait for user approval and an agreed revised spec.
- Preserve `skills/project-room/references/fable-policy.md`: the legacy Qwen policy text (`POLICY_QWEN` in `implementation.py`, mirrored in fable-policy.md's Qwen section) keeps its exact xhigh submit effort, 131,072 output tokens, and blocking waits shorter than 50 seconds for qwen rooms. A new DeepSeek room instead pins `POLICY_DEEPSEEK` together with its snapshotted provider configuration (reasoning effort max; official-backend output defaults to 393,216 and explicitly selected DeepInfra defaults to 131,072 tokens; tool calls can never lower a room's pinned values, and a deliberate configuration change applies only to rooms opened afterwards). Diagnosis before escalation and no delegate self-certification apply to both. Neither policy may be weakened as a workaround, and one provider's settings must never be silently substituted for the other's.
- Keep runtime code dependency-free and compatible with Python 3.10+ on POSIX. Run `python3 -m unittest discover -v` after relevant runtime changes. Tests and CI use fake backends, no account access, paid calls, GPU jobs, or network access; DeepSeek tests inject a fake loopback HTTPS/SSE connection in-process and write synthetic keys into temporary directories, never a real endpoint or the user's saved credential, and no test or model tool reads or prints the user's real provider key files. The authorized live probe reads only the selected backend's key at its normal send boundary. Preserve separate official/DeepInfra credentials, fixed TLS endpoints, explicit backend selection and historical snapshots; never infer a backend switch from a URL or retry rejected settings with a lower budget.
- Keep runtime state outside the installed plugin/cache by default. Do not commit local configuration, environment files, databases, attempts, transcripts, account data, or review receipts. Inspect the staged diff before publication.
- Validate changed manifests and skills with the available plugin-creator and skill-creator validators. Exercise MCP transport with fake backends when interfaces change.
- Do not choose a license or repository visibility without the user's direction.
