# Recovery and evidence

Start with `room_status`, `room_history`, and the saved job ID. A network error or interrupted connection does not establish whether a model received a request. Read the existing job before deciding what to do next.

A matching completed request returns its saved result without another model call. Reusing the ID with different content is rejected. Uncertain delivery, malformed output, wrong session/spec, or model identity failure must not be bypassed by deleting state, changing the model, creating a replacement room, or submitting the same work under a fresh ID.

A user-requested cancellation uses `room_job_cancel`; then inspect its terminal outcome. Do not call cancellation a rollback of changes or proof that no model tokens were used. Work already performed may need inspection.

## Worker startup and the inherited lease

Every job's supervisor acquires that job's `worker.lock` lease before its queued row is published, and hands the already-held descriptor to the detached worker through `pass_fds` instead of letting the worker race to reacquire it after spawn. The worker validates the inherited descriptor (same device and inode as its own `worker.lock`, a regular user-owned file) before treating it as its lease; a launch without a handed-off descriptor (a legacy worker) or with an invalid one falls back to acquiring the lease itself with a bounded retry (40 tries at 50 ms) rather than dying on transient contention. A status read never touches a job's lease until it is at least 10 seconds old, so a worker that is merely slow to start is never mistaken for one that vanished. This applies to the general job supervisor in `project_room.py` and, independently, to the DeepSeek adapter's own per-job worker; see [the DeepSeek delegate guide](deepseek.md) for its ledger and state table.

A host restart is the same boot boundary this document uses for implementation recovery below, and it kills any still-running local worker, including one streaming a DeepSeek response. That DeepSeek job's remote delivery is left unknown — it ends `unknown_delivery` or `failed_after_send` — which stops only that room's DeepSeek lane until the user resolves it at their own terminal; see [room stop and the user-run resolve procedure](deepseek.md#room-stop-and-the-user-run-resolve-procedure). This is independent of whether the implementation job itself qualifies for the audited continuation below.

## Continue after a product decision

Review rounds allow three Fable reviews. If the agents agree, proceed to the authorized handoff. If they need further review, Astra presents the unresolved product tradeoff and waits for your actual answer.

`room_decision_record(room_id, revision, decision)` records that answer against the current spec and permits the next bounded round. It works only when the current round is exhausted and no failed, pending, or uncertain review blocks the room. The audit preserves the exact revision/hash and prior attempt boundary; earlier attempts remain intact. The selected direction is included in Fable's next review context.

This is continuation after a real product decision, not a failure-recovery shortcut. Do not invent an answer, reuse the original build request, renew automatically, or erase history. Revise the specification to reflect the decision and regain exact-revision agreement.

## Local authentication failure

Use `room_job_recover(job_id, diagnosis)` only after diagnosing the saved review job's local sign-in failure. This audits unchanged raw output and preserves the original failure. It requires Claude's exact “Not logged in” result, exit code 1, the saved session UUID, zero token usage, empty model usage, zero API duration/cost, and no structured model output. It cannot recover implementation jobs or unknown delivery; see “Interrupted implementation continuation” below for the two implementation failures that do have an audited path forward. The diagnosis is an explanation, not a substitute for evidence.

Successful recovery returns `not_sent` and makes no model call. After fixing the authentication/configuration cause, submit with a new request ID in the same room. The original UUID remains: if Claude persisted the user/error locally, the next request resumes that session. Do not edit raw output, invent evidence, or retry when the recovery check rejects it.

Use Claude Code's normal login flow and verify with `doctor`. The controller snapshots the original `CLAUDE_CONFIG_DIR` override separately from the resolved directory used to find transcripts. On macOS, explicitly setting even the default directory can select a different authentication namespace. Preserve an originally unset override; do not inject `~/.claude` as a login workaround.

## Interrupted implementation continuation

**Eligibility.** Two implementation-job failures qualify for audited continuation. The first is a positively diagnosed configured model-invocation timeout: a saved error derived from that attempt's exact argv, remaining-time seconds within 60 seconds of the pinned timeout, a receipt with pid and integer return code, no gate directory in the attempt, and no successful terminal result in stdout. The second is the pinned session-usage signature: exit code 1, type `result`, subtype `success`, `is_error` true, `terminal_reason` `api_error`, `api_error_status` 429, `stop_reason` `stop_sequence`, the same session ID, and result text exactly “You've hit your session limit · resets TIME (ZONE)”. Review failures, a still-active or unobserved delivery, cancellation, gate failures, malformed or unrelated results, authentication errors, wrong identity or spec, and generic nonzero exits stay outside this lane. An orphaned worker with no saved bounded-operation result is not eligible.

**Restart boundary and platform assumptions.** Every recovery in this version relies on legacy process receipts: pid, return code, and finished time only. Continuation requires trusted host boot-time evidence strictly later than the original receipt's finished time. Until the host restarts after the interruption, `room_implementation_audit` reports `restart_required` and nothing is prepared or launched; the same boundary applies to a successor that is itself interrupted later. There is no caller waiver, guessed boot time, or automatic restart. Boot time comes from `/proc/stat` `btime` on Linux and `/usr/sbin/sysctl -n kern.boottime` on macOS; both have whole-second precision in the current wall clock. A boot second that is not strictly greater than the receipt time is refused as ambiguous, and an invalid, future, or unreadable boot or receipt time blocks. Clock assumption, stated from the kernel sources rather than from a measurement made by this project: on both platforms the reported boot instant is expressed in the current calendar clock and moves with calendar-clock adjustments. Linux derives `btime` from the current wall clock minus the monotonic boot offset (`getboottime64`), and XNU adjusts its stored boot time by the calendar delta whenever the calendar clock is set (`clock_set_calendar_microtime`, returned through `clock_get_boottime_microtime`, `boottime_timeval` and `sysctl_boottime`). A calendar-clock step after the interruption can therefore move the reported boot instant past the receipt time on either platform without a reboot, and a backward step can hide a real reboot. The boot boundary therefore assumes a trusted, stable host clock between the receipt and the audit; the timestamps alone do not prove an actual reboot under arbitrary clock adjustments. The same-user writer scan (`writer_present`, `inspection_incomplete`) remains the live check for surviving attributable processes. Neither observation proves anything about provider-side availability, and neither can enumerate every possible detached process; they prove only that this host's earlier attributable execution boundary has passed under a stable clock and that no attributable same-user writer is currently visible.

Audit still performs a fresh local observation after the boundary: the same-user process table through `/proc` on Linux, or `/bin/ps` plus `/usr/sbin/lsof` with bounded timeouts on macOS. Any same-user process whose arguments contain the implementation session UUID or the worktree path, or whose current directory is inside the worktree, blocks with `writer_present`; only its pid and match kind are reported, never command lines. Only the auditing process itself is exempt; ancestor shells, editors, or agents are not. After the boot boundary, a numerically reused pid or process group is informational only. Missing or failed inspection blocks with `inspection_unavailable`. A same-user process for which the required current-directory evidence cannot be read blocks with `inspection_incomplete`: on macOS that is a process listed by `ps` without an `lsof` cwd record that a bounded `ps -o stat= -p PID` still shows alive and not a zombie; on Linux it is a `/proc/PID` entry whose `stat`, `cmdline`, or `cwd` read fails with anything other than the process having exited. Processes verified gone or zombie during the scan are counted as `disappeared` and never block; other users' processes are counted as skipped and never read. This is deliberately fail-closed: absent evidence is not proof that a process cannot write the worktree, so a host with a same-user process that hides its cwd (for example a non-dumpable agent on Linux) cannot recover until that process ends. Nothing is ever signalled or killed from saved PID data. A free lock proves only that a cooperating controller owner is absent; the boot boundary is what establishes that the old local execution cannot survive. It proves nothing about provider-side state, grants no quota, and does not certify candidate correctness.

**Audit, prepare, and submit.** `room_implementation_audit(room_id, handoff_id, job_id)` is a read-only observation. It runs no model, Qwen, or network call. It returns whether the job is eligible, the interruption kind (`model_timeout`, `session_usage_limit`, or none), the receipt and timeout it read, the pinned spec and candidate identity, a fresh candidate fingerprint with the paths changed since the initial candidate, the evidence digest, the transcript hash and length, a stopped-work observation labelled `legacy` with boot time, boot source, process method, and any matched process by pid and match kind only, the applicable reason codes, and whether a restart is required. It never echoes prompts, argv, raw error strings, private paths, or transcript text, and it does not repair anything.

`room_implementation_recover(room_id, handoff_id, job_id, spec_revision, spec_sha256, candidate_sha256, evidence_digest, diagnosis, remaining_work, authorization, request_id)` re-runs the audit under locks. Every identity, fingerprint, and digest the caller supplies must equal that fresh observation; the call never adopts new bytes to make a mismatch pass. On success it writes an immutable recovery record under the private handoff directory: the original job row, the failed-state snapshot, the evidence hashes, the diagnosis, the remaining work, the user's actual authorization text, a full fresh partial-candidate fingerprint, a byte-exact streamed snapshot of the session transcript, and the stopped-work observation. It moves the handoff projection from `blocked` to `recovery_prepared`. The call is exact-content idempotent on `(room_id, request_id)`: the same request returns the same record with `duplicate=true`, and different content under the same request ID is rejected. Only one prepared or dispatched recovery may exist per interrupted job.

Exactly one transcript for the session UUID must be discoverable under the configured projects directory, with metadata matching the expected worktree; a predicted path cannot bypass that uniqueness check. Its bytes are snapshotted when the recovery record is written. Both audit and dispatch require the live file to still equal the last snapshot. After the successor starts, the live transcript may keep growing, but the captured prefix must stay byte-identical; a rewritten prefix blocks the successor before identity evidence is even checked, with reason `transcript_prefix_changed`, and later audits verify against the earlier snapshot.

`room_implementation_submit(room_id, handoff_id, request_id, recovery_id?)` dispatches the one authorized successor when called with `recovery_id`. At dispatch, and again inside the worker before any model launch, the controller rechecks identity, current agreement, candidate bytes, evidence hashes, the exact transcript snapshot, the original worker lease, the boot boundary, and current writers.

**What the successor receives.** The successor is a new job ID with a new request ID and a new `attempts/NNNN` directory. It resumes the same implementation session UUID with `--resume` and an explicit continuation packet: the recovery ID, the interruption facts, the candidate binding with changed paths, the diagnosis, the remaining work, the recovery authorization, and any pending correction request. Fable must inspect the existing partial work before editing it; nothing from the interrupted attempt counts as already verified. Gate results and acceptance are cleared for the new attempt. A completed successor then goes through the ordinary Astra review, correction, and later spec workflow like any other implementation result.

**Immutability and lineage.** Original job columns, attempt directories, the pinned manifest, config, spec, history, `initial_candidate`, the recovery record, and its transcript snapshot never change; the live session transcript may only grow by the successor's own appended records. The old job stays uncertain and visible in status with `superseded_by` pointing at its successor. Only the exact predecessor of an authorized successor is exempt from blocking the room; unrelated uncertain jobs and the newest unresolved attempt still block.

If a crash leaves the registry and the handoff projection out of step, audit reports `projection_out_of_sync` and repairs nothing. Call `room_implementation_recover` with a new request ID: it reconciles the projection under the required locks (an unregistered or already-invalidated preparation returns to `blocked` with an audited history entry) before running the fresh audit.

**Pre-launch failure.** A worker spawn failure, or a deterministic recheck refusal before any model launch, records the successor job as failed and the recovery as invalidated. It returns the handoff projection to `blocked` for the same original interruption, keeps every record, and permits a fresh audit and a new recovery request. An invalidated record does not unlock ordinary submits. Unknown worker disappearance after launch stays uncertain; it is never converted to “proven unlaunched.” No automatic retry or re-dispatch ever happens.

Audit touches no room, job, or handoff state, but acquiring its locks creates or updates the small `.lock` and `worker.lock` files inside the existing private directories; it refuses instead of recreating a missing job directory. A successor whose worker ends without any classifiable result (host crash or kill during the run) stays uncertain and blocks the room, and its dispatched recovery is neither consumed nor invalidated: that unknown outcome is deliberately not converted into a proven unlaunched result.

**Honest limits.** Keep three things separate. The original job's diagnosed failure never changes; it stays exactly what its receipt and evidence showed. A prepared and dispatched successor is only a newly authorized continuation, not proof that the earlier candidate was correct or that the new attempt will succeed. Verified acceptance still comes only from Astra's independent review of the successor's delivered behavior and evidence, the same as any other implementation. Freeing local locks and clearing the boot boundary prove only that this host's earlier execution cannot still be writing; they say nothing about provider-side session state, grant no quota, and do not certify candidate correctness. Reason codes you may see include `restart_required`, `boot_evidence_invalid`, `inspection_unavailable`, `inspection_incomplete`, `writer_present`, `cooperating_owner_active`, `job_not_eligible`, `receipt_invalid`, `receipt_time_order`, `model_finish_time_order`, `gate_directory_present`, `error_not_diagnosable`, `contradictory_stdout`, `evidence_missing`, `evidence_unsafe`, `evidence_oversized`, `transcript_missing_or_ambiguous`, `transcript_unparsable`, `transcript_worktree_unbound`, `transcript_worktree_mismatch`, `transcript_unsafe`, `transcript_oversized`, `transcript_changed`, `transcript_prefix_changed`, `transcript_unreadable` (the live transcript could not be read; refused without being treated as tamper), `candidate_changed`, `evidence_changed`, `spec_mismatch`, `recovery_already_exists`, `projection_out_of_sync`, and `recovery_binding_mismatch`.

**Evidence binding details.** Session evidence must be the single transcript for the immutable session UUID and must contain at least one exact-session record whose `cwd` is exactly the canonical handoff worktree root (the anchor). Later exact-session records may name directories inside that worktree, resolved canonically, because changing into a project subdirectory is normal work within the worktree. A record naming a directory outside the worktree, a lookalike path prefix, a symlink that escapes the worktree, or a relative or malformed cwd is refused as `transcript_worktree_mismatch`; descendant-only metadata without the root anchor, or no cwd metadata at all, is refused as `transcript_worktree_unbound`. In the session-usage lane the current `model_finished_at` must fall between the process receipt's finish and the state's finish (`model_finish_time_order`); the timeout lane still requires it to be absent or older than the attempt. Every evidence, receipt, record, snapshot, and transcript read is reached only through user-owned directory descriptors below a trusted root (the handoff directory, the configured Claude projects directory, or an explicit transcript template's parent). The handoff root is bound to the directory that was validated: its identity is captured before the pinned inputs are verified, must be unchanged afterwards, the single root descriptor held for the whole operation must open to that exact identity, and the manifest, state and pinned inputs are re-verified through that descriptor; a directory swapped for a symlink or replaced at any later moment is refused before any byte below it is consumed, and every durable write of preparation, dispatch and failure invalidation is performed relative to that bound descriptor: recovery directories are created and opened component by component under it, records, dispatch notes, invalidation notes, the transcript snapshot and the projection are written to temporary siblings created with `O_EXCL|O_NOFOLLOW`, fsynced and renamed into place relative to the same descriptor, and a failed preparation removes what it created. A root swapped at the very moment of a write therefore lands nothing outside the bound directory, while a change already visible before preparation is refused outright. Only the configured prefix above a root is ever resolved (so aliases such as macOS `/var` remain legitimate); nothing below a root is resolved or followed. Within a root: each component is opened relative to the previous descriptor with `O_NOFOLLOW|O_DIRECTORY` and must be a user-owned directory, and the leaf is opened with `O_NOFOLLOW|O_NONBLOCK` and must be a user-owned regular file within the size bound. A symlink swapped in anywhere below the root, including the attempt directory itself, fails to open and is never followed; a FIFO or device never blocks the audit; the handle returned is the validated object itself. Refusals report `evidence_unsafe` / `transcript_unsafe` without reading through the swapped path. While the audit holds the owner locks it re-reads the candidate, the transcript, every evidence file, and the handoff projection immediately before preparation or dispatch; any change during the observation refuses with `evidence_changed` and nothing is recorded. The successor engine binds itself to the registry named in the durable recovery record and by the invoking service: the successor job must be registered, running, and dispatched for that recovery; the invoking process must be a child of the worker process whose pid the registry recorded when it spawned that worker; and that worker's lease must be held. A held lease alone only proves that someone holds it, so the parent-process identity is what ties the invocation to the registered worker. Accepted limits: after a registered worker has died, another same-user process could hold the lease itself and forge the recorded parent pid through pid reuse; that is arbitrary same-user tampering with owned private storage and is outside the boundary this binding defends. Owned reads carry no I/O timeout, so an unresponsive filesystem mounted inside the owned root (for example a stalled FUSE mount) can still stall an audit; the descriptor-relative opens defend against swapped symlinks, FIFOs and devices, not against a hanging filesystem. A dispatch file, a caller-supplied identity, or an eligible callback cannot replace that registration, and an unauthorized invocation cannot reach a model launch while the registered worker holds the lease.

**Launch truthfulness.** The successor's `launched_at` is recorded only from the spawn receipt (`process-start.json`) that the engine writes immediately after the model process exists; nothing is marked launched beforehand. A failure or cancellation before process creation (output files, or the process-creation call's own cleanup-guaranteed failures) is a proven non-launch: the successor is refused (`model_spawn_failure` or `cancelled_before_launch`), the unlaunched attempt files are set aside rather than deleted, the prepared projection is restored, and the recovery is invalidated so a fresh audit and recovery request may proceed. An interruption that lands inside process creation itself is recorded as `launch_state: unknown`: whether a model process exists cannot be proven, so the successor stays blocked and unclassifiable, the recovery row stays dispatched, and the registry only records a `launch_unknown` event. That state is an expected limit of this version: no operation converts unknown delivery into a retryable non-launch, and the room remains blocked until the user decides on a separate supported path. The start receipt is written immediately after the process exists and the projection is persisted at that moment; if that receipt is lost to a signal or write failure, the exit receipt that the engine writes only for a process that existed still proves the launch. A process that was created and then interrupted (timeout, session limit, or cancellation after creation) is a post-launch interruption: the recovery is consumed and the successor becomes a new preserved failure needing its own diagnosed recovery after another restart.

## Audited verification-only retry after a completed model result

**Eligibility.** This lane covers a different failure than the interrupted-implementation lane above: the model process returned normally with a valid successful terminal result and a validated structured report, the candidate was snapshotted, and then one of the pinned verification gates hit the pinned gate timeout (default 300 seconds), leaving the handoff `blocked` and the job `uncertain`. The lane audits that exact shape and reruns only the pinned gates, never the model, in an isolated copy of the audited candidate. It does not apply when the model itself timed out or hit the session limit — use the lane above for that — when the model result was not a successful terminal result or was a `scope_change`, or when the report or primary-producer identity fails validation. The audit also reconstructs the complete expected model invocation from the pinned configuration — the executable, every pinned extra argument, and the print/output-format/model/session/schema arguments — and refuses `argv_mismatch` when the saved argv differs in any element, including an added argument.

**Isolated offline verification boundary.** The boundary is always reported as `isolated_copy`: a fresh private copy of the audited candidate, built from bounded owned reads with per-entry digest, mode, and path-type checks, run with a fresh private `TMPDIR` and `PYTHONDONTWRITEBYTECODE=1`. The lane fingerprints the candidate with its own bounded helper, matching the exact structure and digest of the implementation engine's own candidate snapshot so historical snapshots compare equal: every entry is stat-checked before any byte is read; files larger than 64 MiB, a total above 1 GiB, more than 100000 entries, or paths deeper than 64 components refuse (`candidate_oversized`, `candidate_path_unsupported`); symlink components are never followed; special entries refuse (`candidate_unsupported_entry`); and a file that changes or grows while it is being hashed refuses (`candidate_changed`) — nothing unbounded is read. This is not an OS sandbox, and each observed fact proves only what it actually measures. A free original worker lease and job lock prove only that no cooperating controller owner is active. A gate receipt return code of -15 proves only that the direct gate child died on the group SIGTERM. An empty process group proves group members are gone, though pid reuse can only cause a false refusal. The same-user writer scan proves no observable attributable process at that instant, fail-closed to `inspection_incomplete` on macOS when `lsof` has no cwd record. Candidate equality checked before and after a gate proves equality at those instants only, never the absence of transient, ignored, external, or later writes. None of this proves every descendant process stopped; an invisible survivor influencing shared user-level state remains a disclosed residual that the user accepted only for this project's identified offline unit tests and local validators, not for arbitrary gates.

**Audit and retry.** `room_verification_audit(room_id, handoff_id, job_id)` is read-only: it runs no model, network, or gate, and repairs nothing. It returns `eligible`, `boundary` (always `isolated_copy`), `reasons`, `identity` (handoff_id, job_id, spec_revision, spec_sha256, baseline_commit, session_id), `generation` (attempt_count, model_return_code, the report's outcome, implementation_complete, remaining_gap_count, primary_model), `failed_gate` (index, count, argv_sha256, the receipt's return_code and finished_at, timeout_seconds, and pinned_gate_timeout_seconds), `gates_sha256`, `candidate` (sha256, head, path_count, changed_vs_initial), `transcript` (sha256 and length, which must equal the saved `identity_evidence.transcript_sha256` exactly), `evidence_digest`, a `stopped_work` observation, `budget` (original_seconds, minimum_seconds, a maximum_seconds of 7200, and a proposed_seconds of 900), `supported_scope`, and `limitations`. It never echoes prompts, argv, raw error text, private paths, or transcript text.

`room_verification_retry(room_id, handoff_id, job_id, spec_revision, spec_sha256, candidate_sha256, evidence_digest, gates_sha256, gate_timeout_seconds, diagnosis, authorization, request_id)` re-audits under the same lock order used elsewhere in this document — room control, then the handoff directory, then the original job directory, then the original worker lease — and requires every supplied value to equal that fresh audit exactly; it never adopts new bytes to make a mismatch pass. `gate_timeout_seconds` must validate as an integer, never a boolean, no less than the original pinned gate timeout and no more than 7200 seconds; 900 seconds is the proposed value. On success it writes an immutable record under the private handoff directory at `verifications/<verification_id>/record.json`, containing a byte-exact transcript snapshot, the failed-state snapshot, the evidence hashes, the boundary, the gate-specific authorization text, the diagnosis, and the budget; registers the verification in the controller registry; and dispatches exactly one asynchronous verifier job (a new job ID, kind `verification`). The call is exact-content idempotent per `(room_id, request_id)`: the same request returns the existing verification with `duplicate=true`, and different content under the same request ID is refused. It returns `verification_id`, `successor_job_id` (wait on it with `room_job_status`), `status`, `record_sha256`, `budget_seconds`, and the underlying audit.

**What the verifier does.** The verifier binds itself to the registry row, its registered parent worker pid, and its held lease, then repeats the full audit before anything runs — a refusal at this point is `refused_before_launch`, the job ends `failed`, the verification row becomes `invalidated`, and nothing was spawned. It moves the handoff projection to phase `verifying`, verifies the full original candidate and index, and builds a fresh private copy of the audited candidate under `verifications/<id>/candidate` from bounded owned reads with per-entry digest, mode, and path-type checks: regular files only, every symlink entry refused as unsupported scope, a 64 MiB per-file bound, a 1 GiB total bound, and entry-count and path bounds; original repository metadata such as `.git` is never copied. It then runs exactly the pinned argv arrays, in order, with `cwd` set to the copy, a fresh private `TMPDIR`, `PYTHONDONTWRITEBYTECODE=1`, and the environment marker `PROJECT_ROOM_VERIFICATION_ID=<verification_id>` — correlation evidence only, never authority to signal a process — under the recorded budget, with spawn and exit receipts. It re-verifies the copy before and after every gate; a modified audited file or a newly created non-ignored path, classified with a read-only `git check-ignore` against the original repository, interrupts the run. It writes an immutable `outcome.json` before touching the mutable projection, re-verifies the original worktree still equals the audited candidate before projecting, and then projects `awaiting_astra_review` with the new gate results (stored privately under `verifications/<id>/gate-N/`) and `gates_passed`. The original attempt directory, the original job row, and its error text are never modified; the failed state is preserved in the record's `failed_state_snapshot` and in `verification_history`.

**Interruptions, crashes and cleanup.** At the end of a run the verifier computes the outcome bytes, then registers their SHA-256 in the registry row (`implementation_verifications.outcome_sha256`) while the row is still `dispatched` — an update bound to the owning execution: the verifier must still be the registered worker's child, the row must still be dispatched for that successor, and the worker's lease must still be held, and the digest can be set only once (a registration failure here, for example lost ownership, is itself recorded as an interrupted outcome with reason `outcome_registration_failed`, `copy_bounds_exceeded`) — then writes `outcome.json`, then projects the handoff state; this binds the digest to the owning execution and does not defend against an actor who controls all trusted owner state (registry, lease, and worker). A gate timeout, a cancellation, or a candidate change during the run is instead preserved as an interrupted verification — `gate_timeout:N`, `cancelled`, `candidate_changed`, `gate_changed_candidate`, `gate_created_candidate_path`, or `copy_mismatch` — and the projection returns to `blocked` with the original error intact, the verifier job ends `uncertain`, and nothing retries automatically; a later, separately requested retry needs a fresh audit. Crash reconciliation on the next mutating controller call never reruns a gate: a dispatched row whose successor is no longer active and whose registered digest matches `outcome.json`, whose every saved gate stdout/stderr and `process-result.json` digest matches the outcome, and whose current original candidate still equals the audited candidate is projected — or, if the engine had already projected before the crash, settled against the already-projected gate results — and the row becomes `consumed` with reason `reconciled`; a registered interrupted outcome instead returns the projection to `blocked` and marks the row `interrupted`; a row with no registered digest — the worker vanished before registration, or a merely planted `outcome.json` — is invalidated as `verifier_incomplete:unregistered_outcome` and is never projected; changed logs, receipts, or candidate bytes after a durable outcome invalidate as `verifier_incomplete` with the detail. A reconciled edge's successor job row stays `uncertain` — it is never rewritten — but is exempt from blocking the room through that validated edge. After the gates, the verifier checks for survivors: its own gate pids and process groups, any process whose cwd or arguments name the verification directory, and any same-user process whose environment or arguments carry `PROJECT_ROOM_VERIFICATION_ID=<verification_id>`. Linux reads `/proc/<pid>/environ` of same-user processes with a bounded read, where a denied or oversized read counts as incomplete and refuses; macOS parses `/bin/ps -E`, which appends the environment of the caller's own processes to the command column, so an unreadable environment cannot be distinguished there from an empty one and a same-user process that hides its environment is not attributable by marker on macOS, though the cwd, argument, and process-group observations still apply; no environment value is ever retained or reported, only pids and the matched marker, and the marker remains correlation evidence only — nothing is signalled from it. If any survivor is observed, or inspection is incomplete or unavailable, cleanup is deferred and the run is not projected as a pass: the outcome is recorded as interrupted with reason `survivors_observed` (or `inspection_incomplete` / `inspection_unavailable`), the row becomes `interrupted`, the projection returns to `blocked` with the original error, the private copy stays in place and is never hidden, and the next audit for that attempt refuses with `gate_process_present` — the matched pid carries match kind `marker_env` — until the survivor exits. Otherwise cleanup removes the private copy and its `TMPDIR`, still only inside the owned verifier directory.

**Lineage and acceptance.** The original uncertain job stays uncertain, with `superseded_by` pointing at the verifier job. Only a registered and validated edge exempts it from blocking the room: a `consumed` row whose `record.json` and `outcome.json` still hash to the registry's recorded digests, whose outcome names the same room, handoff, attempt, predecessor, and successor, and whose successor job succeeded — or, for a row consumed by crash reconciliation with reason `reconciled`, whose successor job is simply no longer active, since the outcome itself accounts for that vanished worker; or a `dispatched` row whose successor is still active. Earlier interrupted verifier jobs for the same original job and attempt are exempt only through that same validated lineage. A tampered or merely claimed record, a planted outcome file without a registry row, or a caller-supplied path never exempts anything, and no other uncertain job is unblocked. Historical edges are validated against their own immutable evidence, never against the live candidate or transcript, so they stay valid after a legitimate later correction. Existing model-timeout recovery edges keep their existing registry-only semantics, tracked separately as issue #71. A passed suite is gate evidence only: `room_implementation_review` still refuses acceptance of a report with `implementation_complete` false, remaining gaps, or a non-completed outcome, and Astra must request a normal correction with `room_implementation_revise`, which resumes the same saved Claude session with the retry's gate logs as previous gate output. Later corrections keep the original pinned 300-second gate budget, and each may need its own separately authorized verification retry; the retry never changes the pinned profile.

**When it cannot run.** The lane refuses when: the model itself timed out or hit the session limit (use the interrupted-implementation lane above instead); the model result was not a successful terminal result, was a `scope_change`, or its report or primary-producer identity fails validation; model delivery is unknown; the failure is not the exact pinned gate-timeout text for the identified gate; an active recovery or verification already exists, or the projection is out of sync; the candidate or HEAD moved since the snapshot; there are open findings or a stale agreement; a live cooperating owner is present (`cooperating_owner_active`); a surviving gate process or writer is present (`gate_process_present`, `writer_present`); process inspection is unavailable or incomplete; receipts or evidence are malformed or missing; the transcript no longer hashes to the saved identity hash — appended bytes, rewritten history, or a missing or ambiguous file, with no append tolerance; a pinned gate argv literally names the original worktree path (`gate_names_worktree`); or the candidate contains symlinks, oversized files, or unsupported paths. Gates that need original repository metadata (for example git commands) or other external mutable state may also be ineligible, and the literal argv check cannot catch every reference inside arbitrary executable code; only the actual approved offline suite is verified to work in the supported copy.

**Consume settlement.** The worker consumes a verification row only when the durable outcome that hashes to the engine-registered digest records a completed result. If the frozen job result cannot be trusted or read, the row is left dispatched and settled from the registry digest instead (the record, outcome chain, gate log and receipt digests, projected gate results and current candidate must all re-verify, giving `consumed` with reason `reconciled`); a genuine completion is never invalidated by a frozen-result problem, and only a row with no registered digest is invalidated as `verifier_incomplete:unregistered_outcome`.

**Read bounds inside the verifier.** Every byte the verifier visits is read through an owned descriptor with a bound that holds during the read, not only at the stat before it: a copied or gate-created file is read at most one byte past the smaller of the per-file limit and the remaining aggregate budget, so a file that grows after its stat is refused, and the bytes visited across the whole copy, ignored files included, never exceed the total limit. Ignore rules keep their candidate semantics for ordinary in-bound files, but they never lift these resource bounds; exceeding one interrupts the run with `copy_bounds_exceeded` and the copy-relative paths that exceeded it. Generated listings are captured with the same discipline: the lane's own `git ls-files`, `git rev-parse`, `git check-ignore` and, on macOS, `/bin/ps -E` outputs are read through a bounded capture (16 MiB for git listings, 64 MiB for the process listing, 60 KiB of stdin for check-ignore) that stops only the child it created and refuses beyond the cap (`candidate_oversized` for a candidate listing, `inspection_unavailable` for the process listing, a failed ignore classification for check-ignore), so nothing is buffered without bound and no arbitrary process is ever signalled; a refusal never launches a gate or the model.

**Honest limits.** Keep the same things separate as in the interrupted-implementation lane above. A passed verification run is gate evidence only, never proof of product correctness or that the original candidate was already correct. The isolated-copy boundary is not an OS sandbox: it does not prove every descendant process stopped, and an invisible survivor influencing shared user-level state remains a disclosed residual accepted only for this project's identified offline unit tests and local validators, not for arbitrary gates. Reason codes you may see include `job_not_eligible`, `handoff_integrity`, `attempt_identity_mismatch`, `evidence_unsafe`, `evidence_missing`, `evidence_oversized`, `receipt_invalid`, `receipt_time_order`, `argv_mismatch`, `model_result_mismatch`, `report_mismatch`, `report_invalid`, `scope_change_outcome`, `identity_mismatch`, `gate_index_ambiguous`, `gate_evidence_missing`, `gate_receipt_invalid`, `gate_error_mismatch`, `timeout_seconds_invalid`, `timeout_seconds_out_of_range`, `gate_names_worktree`, `spec_mismatch`, `open_findings`, `candidate_unreadable`, `candidate_changed`, `candidate_head_moved`, `candidate_unsupported_entry`, `candidate_oversized`, `candidate_path_unsupported`, `transcript_missing_or_ambiguous`, `transcript_unparsable`, `transcript_worktree_unbound`, `transcript_worktree_mismatch`, `transcript_unsafe`, `transcript_oversized`, `transcript_changed`, `transcript_prefix_changed`, `transcript_unreadable`, `cooperating_owner_active`, `writer_present`, `inspection_unavailable`, `inspection_incomplete`, `gate_process_present`, `survivors_observed`, `verification_already_exists`, `projection_out_of_sync`, `verifier_incomplete:unregistered_outcome`, `outcome_registration_failed`, `verification_binding_mismatch`, and `evidence_changed`.

## Identity reconciliation in the low-level review engine

Claude may hash project directory names when paths are long. `session_paths.py` locates only the saved UUID filename under the configured projects directory and validates session/worktree metadata. It does not read unrelated sessions or choose one by recency. Ambiguous or mismatched evidence stays blocked.

When a saved successful review fails identity verification because the predicted transcript path is absent, the controller can automatically locate that exact session and perform an audited reconciliation. It does not resubmit the review.

`room.py reconcile` provides the same narrow validation for a saved successful terminal response rejected solely for mixed-model identity. It revalidates the primary `StructuredOutput` producer against the explicit session transcript, exact returned payload, session UUID, expected model, and attempt time window. It makes no subprocess/model call and preserves the original failure and raw evidence.

From the plugin directory, use the room engine directory and actual request ID:

```sh
python3 room.py --room /absolute/private/path/to/engine-room reconcile \
  --request-id ACTUAL_REQUEST_ID \
  --session-transcript /absolute/private/path/to/SESSION_UUID.jsonl \
  --note-file /absolute/private/path/to/evidence-note.md
```

The evidence note explains what was examined. This command does not recover a nonzero process exit, malformed reply, wrong session/spec, or unknown delivery. Where the engine supports a legacy verifier error, any inferred zero exit code remains explicitly distinguished from a measured one. Never manufacture transcript evidence, search unrelated sessions, or expose model thinking.

## Scope discoveries and corrections

An implementation `scope_change` creates a blocking issue. Register a strictly newer specification, record the issue's disposition and rationale against that revision, and obtain renewed Astra/Fable agreement before another handoff. The old consensus cannot clear the discovery.

For a known completed implementation within the same scope, record actionable rejection, call `room_implementation_revise`, then submit a new implementation request ID for that handoff. Rerun gates and independently review the correction. This repair path does not apply to uncertain delivery.

Optional enhancements are proposed visibly and filed as project GitHub issues under existing authorization. Preserve the proposal and verified link locally, and check existing records before retrying issue creation after an interruption. If no tracker is available or filing failed, show the proposal and state that filing is pending; do not invent an issue URL. Continue agreed work while awaiting the user's opinion and scope approval. Creating an issue does not authorize implementing the enhancement.

## Diagnose capabilities separately

- A successful MCP initialization/tool list proves the server process and tool schemas are available.
- A successful health request proves only the reported health/model/window facts at that time.
- A completed generation proves inference for that request; it does not independently prove task correctness.
- A TCP timeout proves the target port was unreachable within the probe window. It does not distinguish an offline host, network/VPN route, firewall, or listener problem.

A denied authenticated request must not be retried through another tool or wrapper to evade the denial. Continue safe independent work, use a permitted diagnostic when it answers the remaining question, and report the exact blocked action and reason if authenticated access remains necessary.
