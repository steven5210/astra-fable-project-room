# Architecture

`ao_prompt_metrics.py` records tagged components of the actual outgoing packet and
projects saved status with a separately verified selected receipt. It keeps prompt
bytes distinct from delivery, native usage and quota. The explicit
`ao_evidence_audit*` modules read one saved request's bound Claude evidence through
bounded ownership and source checks before emitting only the closed diagnostic
schema; `ao_usage_audit.py` reuses those bounded bindings and intervals to report
explicit native parent, worker and API delegate usage without participating in
dispatch or acceptance. See
[AO diagnostics](diagnostics.md) for the schemas, limits and read-only boundary.

The package separates the agent workflow from durable execution:

- `skills/project-room/SKILL.md` supplies Astra's roles and backend selection. AO rooms work from `references/ao-card.md`, a per-phase operator card that names the section of `references/ao.md` to open for each exception. Legacy rooms follow `references/legacy.md`.
- `project_room_mcp.py` exposes local stdio tools. The plugin manifest starts it from the installed plugin root.
- `project_room.py` provides setup, diagnostics, a project/feature room registry, and the CLI equivalent of the MCP operations.
- `ao_acceptance_extension.py` audits and grants one exact additional independent acceptance review after the ordinary AO allowance. Its append-only grant/consumption journal preserves native ownership, prior evidence and single-use dispatch semantics; see [acceptance-review continuation](../guides/acceptance-review-continuation.md).
- `ao_spec_review_budget.py` classifies every `spec_review` intent, including a re-review claim, under the same strict verdict contract the agreement path applies to the request's own immutable spec record: accepting completed reviews never consume the three-attempt debate budget, every other completed review does, and every dispatch regardless of state counts toward the hard ceiling of five. Its summary feeds `ao_room_status` read-only; `ordinary_review_capacity` reports budget capacity only — semantic holds, pending format recovery and other send gates can still refuse a review.
- `ao_review_extension.py` audits and grants the room's one exact additional charter review once the debate budget is exhausted below the dispatch ceiling, either for a retained accepted candidate or, before any acceptance, for an unaccepted candidate whose latest completed engineering turn proposed a scope change. Both lanes share one grant/consumption journal, receipt and room-wide counter; see [one additional AO charter review](../guides/one-charter-review-extension.md) and [pre-acceptance exact-spec review extension](../guides/pre-acceptance-review-extension.md).
- `ao_spec_rereview.py` audits and grants the room's one-ever explicitly authorized exact-spec re-review after that extension was consumed by an additional review that completed with a retained negative or noncanonical-negative verdict and the operator registered the corrected next revision. The intent after the extension's granted position is never admitted above the five-dispatch ceiling. One named intent is consumed durably before POST with no refund, renewal or second grant; see [one authorized exact-spec re-review](../guides/spec-rereview.md).
- `ao_spec_verdict_recovery.py` audits, grants and validates the budget-neutral strict-format re-ask of a completed prose-only specification review, once per source review at any dispatch count. Each source keeps an independent chain of create-once grant/intent/completion/agreement/closure records under `spec-verdict-recovery/chains/<source_request_id>/`, rotating finished pointers into retained history; legacy flat-chain rooms read unchanged. An agreed chain credits its source as an accepting review; a closed or settled-failure chain leaves it as debate. See [strict-format re-ask](../guides/spec-verdict-format-recovery.md).
- `room.py` supplies the underlying specification-review engine: immutable specs, exact digests, persistent Claude identity, idempotency, verification, audited recovery, and bounded review rounds continued by recorded user decisions.
- `implementation.py` supplies the authorized implementation lifecycle and validation evidence, saving each model or gate stage start before the child runs so status can report accurate countdowns.
- `progress.py` derives the additive read-only `progress` object for job status from owned registry, review-turn, and handoff state plus a bounded scan of the exact owned session transcript; it never spawns, calls a model, or edits state. See [progress](progress.md).
- `ao_progress.py` derives the read-only, per-request `ao_room_progress` view (task-list plan, Agent launches, rate limits, and the additive `deliverables` lineage/closure projection folded from the same native task-tool rows) from a bounded scan of the registered AO transcript; it performs no state mutation, hold release, receipt or report replacement. See [progress](progress.md).
- `ao_current_summary.py` derives the additive, read-only `current_summary` object carried by `ao_room_status` (full and compact) and `ao_room_progress`: the latest engineering request, the newest digest-checked captured result, one status per delivery-ladder rung, the verification/acceptance relation to the captured baseline and a closed set of inconsistency codes. It reads saved room records only, performs no state mutation, transcript read, gate run or model call, and decides nothing. See [progress](progress.md).
- `heartbeat.py` writes a bounded private worker liveness record from the existing supervision loop; it never changes execution policy.
- `handoff_status.py` projects verified saved handoff metadata through an allowlist without running gates or recovery.
- `recovery.py` classifies an eligible interruption, observes host boot time and local processes, audits the stopped job read-only, and writes the immutable recovery record that an authorized successor job resumes from.
- `session_paths.py` locates only the saved UUID transcript and validates session/worktree metadata, including hashed directories for long paths.
- `qwen_guard.py` wraps an existing upstream stdio server to enforce fixed submit settings and bounded blocking waits.
- `deepseek_adapter.py` is the self-contained stdio MCP adapter for the optional DeepSeek delegate: a durable SQLite-backed job ledger, separate backend-specific key handling, request execution, and export publication. Its normalized configuration deliberately selects the fixed official DeepSeek or DeepInfra transport; the tool family, ledger lifecycle and content/reasoning separation remain shared. It imports nothing from the controller and is copied verbatim into a DeepSeek room's `profiles/` snapshot, so a later package update cannot silently change an existing room. See [the DeepSeek delegate guide](deepseek.md).
- `ao_project_room.py`, `ao_workflow.py`, `ao_delegates.py` and `ao_delegate_launcher.py` form the stock Agent Orchestrator adapter described in the AO skill reference: immutable specs, durable sends, private delegate preparation, exact-candidate verification and independent acceptance outside the repository.
- `ao_quality_review.py` holds the immutable `quality_first_review_v1` instruction and bounded local proof of its actual receipt-backed delivery. `ao_workflow.py` and `ao_instruction_amendments.py` reuse this proof for exactly-once instruction assembly and explicit equivalent-amendment provenance; saved status reports the verified root without changing historical records or acceptance authority.
- `lifecycle_closure.py` holds the immutable `lifecycle_closure_v1` one-time AO amendment (frozen text, version and SHA-256 digest); `ao_workflow.PARTS` delivers it once to a new or retained AO engineer session like the other one-time parts, and `project_room_runtime.RUNTIME_FILES` retains the module so an installed runtime carries it.
- `ao_execution_evidence.py` holds the immutable `execution_evidence_v1` one-time AO amendment (frozen text, version and SHA-256 digest), appended in `ao_workflow.PARTS`; it asks the engineer to put the explicit `task=<id>` token in each Agent launch description so the read-only progress view pairs launches with units by that reference alone, and `project_room_runtime.RUNTIME_FILES` retains the module so an installed runtime carries it.
- `ao_finding_provenance.py` holds the immutable `finding_provenance_v1` one-time AO amendment the same way; `ao_findings.py` is the read-only projection of those report-entry tokens into `ao_room_status.review_followups.engineering.findings` — counts, histograms and bounded redacted items that grant nothing and change no state.
- `ao_timing.py` derives the read-only `ao_room_timing` delivery-timing view (wall-clock intervals per saved request and verification attempt, gaps classified only from saved semantic holds, overlap reported separately) from state.json and bounded receipt reads; it performs no state mutation, transcript read or model call. See [diagnostics](diagnostics.md).
- `ao_response_normalization.py` provides an audited operator-only recovery for a completed response whose valid JSON has surrounding prose. It preserves raw receipts and binds derived evidence to the exact request, spec, response and candidate; it never makes an inference call or manufactures approval.
- `ao_routing.py` generates, snapshots and offline-validates the worktree-scoped native routing configuration of a prepared AO engineer (pinned `pr-sonnet`/`pr-opus` definitions, local settings knobs and deny rules, executable identity, observed AO project rules); `ao_routing_guard.py` is the stdlib-only, deny-only `PreToolUse` guard copied content-addressed into private controller state and run by Claude's hook shell.
- `transcript_audit.py` performs a CLI-only, read-only tool-use audit of one implementation attempt's exact session transcript and its subagent files, counting `mcp__qwen-local__*`, `mcp__deepseek__*`, `Agent`, and `Task` uses without emitting any text or arguments.
- `changeset_tool.py` exposes the separate operator-only plan/apply/audit/resume CLI and Python API. `changeset_core.py` and `changeset_ops.py` validate strict bounded inputs and deterministic edits; `changeset_plan.py` pins exact roots, source/draft/proposed bytes and conditions; `changeset_receipts.py` derives inert receipt templates and validates operator-supplied check statements. `changeset_fs.py` provides descriptor-based metadata/durability operations; `changeset_journal.py` holds cooperative locks, immutable prepared journals and explicit recovery. `changeset_faults.py` is an import-only test seam, never a draft/CLI execution mechanism. See [change sets](changesets.md); these modules do not invoke models, commands or project checks or alter the room acceptance lifecycle.

Runtime data defaults to `~/.project-room` or `PROJECT_ROOM_HOME`. It is independent of plugin installation/cache paths. Claude uses dedicated saved sessions; the controller does not adopt a running Desktop conversation or scrape unrelated chat histories. A recorded message is explicit context, not implicit access to another model's full conversation.

Native transcript capacity. `ao_native_outcome.inspect`, `ao_engineering_transition`'s transition lane and `ao_spec_verdict_recovery`'s one-use format-recovery check each read a complete native history through the one shared `ao_native_outcome.read_complete_transcript`/`iter_transcript_records` reader; `preflight_source` and `validate_registered_source` are read-only `st_size` gates against that same cap, not readers of file content. `ao_progress` keeps its own unchanged bounded 64 MiB tail scan; `ao_evidence_audit_io` and `transcript_audit` are separate read-only diagnostics lanes with their own budgets. The shared reader bounds three things: the complete history at 256,000,000 bytes, one JSONL record at 16,777,216 bytes, and the per-file non-blank record count at 2,000,000; a 1,048,576-byte chunk bounds one read. A record over its budget or a file over its record-count budget always raises one of two refusal strings shared by every caller; a malformed row raises the caller's own message when one is given, else a shared default; every other refusal -- unsafe ownership or size, or a change observed mid-read or between observations -- always uses the caller's own message. The descriptor is opened `O_NOFOLLOW`, then identity-checked by `fstat` before any byte is read (regular file, owner uid, no group/other write, size at or under the cap); the same `fstat`, plus a separate named `lstat`, reverifies identity after the last byte -- inode, size, mtime, ctime, owner uid and mode, so a bare chmod/chown or a same-size rewrite with its mtime explicitly restored is still caught whenever the filesystem records a different ctime (inode timestamps are only as fine as the filesystem's clock granularity) -- and that identical recheck runs again, descriptor still open, after any parse refusal, so a concurrent same-size rewrite or a writer completing a torn final row is reported as changed, never as malformed. Two observations of one history are tied together by digest and size revalidation; the format-recovery lane additionally keeps a prefix digest of its previously retained bytes and refuses outright, rather than guessing, any record whose byte offsets straddle that retained boundary. A history that outgrows any of the three budgets is refused the same deterministic way on every lane that reads it, reported unknown or held; there is no automatic rotation, truncation, prefix fallback or new setting, so growth past a budget requires the operator to act explicitly.

Cost. The reader makes one pass over at most 256,000,000 bytes in 1,048,576-byte chunks, scans each physical line once for its terminator, holds at most one record plus one chunk pending, and parses at most 2,000,000 JSON records; those input, record, record-count, chunk and pending-buffer bounds are enforced by the code and are the only guarantees it makes. Wall time and heap beyond them depend on the interpreter, its allocator and the shape of the rows, because every parsed row is retained as Python objects until the lane has finished with the complete list -- a design choice carried over from the lanes this reader replaced, not something complete-history processing itself requires -- so no universal time or memory bound is claimed. Measured on one development machine (macOS arm64, CPython 3.11, single or few runs recorded in the engineering evidence that accompanied this repair, not in the repository): a valid synthetic history of exactly 256,000,000 bytes and 10,083 records of about 25 KB each was inspected in about 3.0 seconds and read for the transition lane in about 3.8 seconds with a peak process RSS of about 0.44 GB; 2,000,000 minimal records in about 83 MB raised RSS by about 0.9 GB; one 4 MiB record of repeated empty objects parsed to about 28 times its bytes and one 16,777,216-byte record to about 33 times; 16 MiB of bare line terminators, consumed as one run, took about 0.07 seconds, and 16 MiB of whitespace-only lines, each scanned and skipped individually, took about 2.2 seconds. Extrapolations from those shapes, not measurements: roughly 8.4 GB if a 256,000,000-byte history consisted entirely of 16 MiB records of empty objects, and roughly 34 seconds for a cap-sized history of whitespace-only lines. Whether repeated empty objects are the most expansive admitted shape is unproven: nested empty arrays, for example, create one container object for every two input bytes up to the interpreter recursion limit, beyond which the parse fails and the record is refused as malformed. The 256,000,000-byte cap is about four times the largest native history observed when this repair was made; the per-record and record-count budgets are headroom estimates, not measurements.

Claude is launched with argument arrays and the configured exact model. The original `CLAUDE_CONFIG_DIR` override is preserved separately from the resolved transcript lookup directory, so an originally unset override stays unset. The review engine distinguishes a primary result producer from auxiliary usage. Identity reconciliation and local authentication recovery preserve the original evidence and never make a model call; see [recovery](../operations/recovery.md). The plugin does not extract account credentials or introduce a hosted relay.

Implementation handoff requires a clean Git source checkout and pins its baseline commit. The isolated worktree holds an uncommitted candidate. Independent gates run in that worktree; fingerprints bind working files, Git index entries, and HEAD so later changes cannot inherit stale evidence. Acceptance records the candidate. A scope discovery creates a blocker requiring a newer spec revision and renewed consensus. The Astra skill then performs integration with normal repository tools when delivery was requested; publication still follows the user's scope. These are separate from the controller's acceptance operation.

`recovery.py` only applies to an implementation job stopped by a configured model-invocation timeout or the provider's session-usage-limit signature; every other failure stays outside its classifier. Audit and recovery require host boot time strictly after the original receipt's finished time, read on Linux from `/proc/stat` `btime` and on macOS from `/usr/sbin/sysctl -n kern.boottime`; the fresh same-user process scan still runs in the same observation, and every reason (for example `restart_required` and `writer_present`) is reported together. The immutable recovery record, the failed-state snapshot, the evidence hashes, and the streamed transcript snapshot live under the private handoff directory next to the original job, and the registry table `implementation_recoveries` indexes them by room, handoff, and request ID. Lineage keeps a superseded job visible and uncertain while exempting only its authorized successor from the idle guard that otherwise blocks a room on any unresolved attempt. Every controller recovery operation acquires the room control lock, then the handoff directory lock, then the original job directory lock, then the original worker lease, in that order; the worker's pre-launch recheck already holds the handoff lock and takes only the original job lock and lease. None of these blocks, and any failure reports `cooperating_owner_active`. Private evidence, records, snapshots and transcripts are read only through user-owned directory descriptors below a trusted root (`O_NOFOLLOW` per component, `O_NONBLOCK` leaf), never through path-based opens that a swapped symlink or FIFO could redirect or block; the handoff root descriptor is bound to the directory identity captured around validation and held for the whole operation, so a root swapped afterwards is refused before any read, and every durable recovery write (preparation, dispatch, invalidation) is created, written and renamed relative to that descriptor rather than by path. The successor engine binds to the registry rows, the parent worker pid recorded at spawn, and the held lease; `launched_at` is recorded only from the spawn receipt written after the model process exists, and an interruption inside process creation stays `launch_state: unknown` and blocked.

MCP job submission and model execution are distinct. A job ID lets an active Astra turn wait in bounded intervals and lets a later turn resume after disconnect. Persistent jobs do not automatically trigger an idle Astra task. Deployment, PR publication, notifications to third parties, and schedules are outside the room's automatic lifecycle unless the user explicitly includes them.

The Qwen proxy enforces tool parameters rather than model quality or server configuration. Fable's engineering judgment determines whether a delegate is suitable. Model/window/health verification must be reported separately from tool discovery, and unavailable capabilities must stay visible.

A DeepSeek room's `profiles/` directory snapshots the adapter source and its normalized key-free configuration, including backend, exact model, endpoint and output budget, records their SHA-256 digests plus the room's granted export directory in `settings.json`'s `provider_inventory`, and grants the implementation profile `--add-dir` access to exactly that room's export directory. `implementation.resolve_provider` pins that inventory into the handoff identity at prepare time, `implementation._continue_run` re-verifies every snapshotted byte before each attempt (initial, correction, or audited successor), and the adapter refuses to serve or run a job when its own copy disagrees. Paths are pinned as strings; only the export directory's identity, not an inode, is reverified at each use, so it may be recreated when merely missing. See [the DeepSeek delegate guide](deepseek.md).

The job supervisor in `project_room.py`, and the DeepSeek adapter's own worker, both acquire a job's `worker.lock` lease before publishing the queued row and hand the held descriptor to the detached worker through `pass_fds`, rather than letting the worker race to reacquire the lease itself; a worker launched without a valid inherited descriptor falls back to a bounded retry instead of dying on transient contention, so a slow-to-start worker is never mistaken for one that vanished. See [recovery](../operations/recovery.md).

Enhancement proposals are durable room records that Astra surfaces for the user's opinion and scope approval. Astra creates or links issues through the available GitHub connector or CLI in the feature project's repository, then records the verified link; the model report itself does not execute issue operations. Filing authorization does not expand implementation scope. Missing tracker access leaves an explicit pending-filing record.
