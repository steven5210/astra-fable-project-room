# DeepSeek delegate

This is the setup, invocation, and evidence reference for the optional DeepSeek delegate provider, the newer alternative to the [legacy Qwen provider](../skills/project-room/references/fable-policy.md). A room pins exactly one first-tier delegate provider — DeepSeek, legacy Qwen, or none — at creation, and this document covers only the DeepSeek path. See the [README](../README.md) for the one-time setup summary and [architecture](architecture.md) for how the adapter fits into the rest of the controller.

## Choose the transport

The `deepseek` tool family supports two deliberately selected backends. Its shared tool name does not identify the host; inspect `backend`, endpoint and exact model in diagnostics.

| Configuration | Official DeepSeek | DeepInfra |
| --- | --- | --- |
| `backend` | `official` (compatibility default when omitted) | `deepinfra` (explicit selection) |
| Fixed request URL | `https://api.deepseek.com/chat/completions` | `https://api.deepinfra.com/v1/openai/chat/completions` |
| Default model | `deepseek-v4.1-flash-expires-on-0910` (historical preview pin) | `deepseek-ai/DeepSeek-V4.1-Flash` |
| Deep effort / output cap | `max` / 393,216 tokens | `max` / 131,072 tokens |
| Context / evidence basis | 1,048,576 / provisional V4 family assumption | 1,048,576 / advertised public model metadata |
| Default request timeout | 9,891 seconds | 3,337 seconds |
| Default private key | `<home>/secrets/deepseek-api-key` | `<home>/secrets/deepinfra-api-key` |
| Complete key-free example | [Official](../examples/deepseek-provider.example.json) | [DeepInfra](../examples/deepinfra-provider.example.json) |

The [DeepInfra model API guide](https://deepinfra.com/deepseek-ai/DeepSeek-V4.1-Flash/api) names the hosted model and endpoint; its [public metadata](https://api.deepinfra.com/models/deepseek-ai/DeepSeek-V4.1-Flash) advertises the output and context limits above. These are provider claims, not measurements by this adapter. The [Chat Completions schema](https://docs.deepinfra.com/api-reference/chat-completions/openai-chat-completions) includes `reasoning_effort: "max"`. A successful tiny live probe establishes acceptance of that request, not how the hosted model applies effort, maximum-length generation, model equivalence or quality. A rejected pinned setting fails explicitly without lowering it or changing hosts/models.

Select `backend` in the private configuration before opening a new room. A mismatched `base_url`, a model of the other transport's identifier shape, or the other backend's default key filename is refused. Custom key paths remain supported; keep different providers' credentials in different files. Official model syntax has no slash; DeepInfra requires one `organisation/name` namespace. Endpoints are fixed in code and cannot be overridden by URL, proxy or redirect. Setup never migrates or rewrites saved rooms, historical job rows or pinned adapter/configuration/policy bytes.

### DeepInfra data handling

DeepInfra's [data policy](https://docs.deepinfra.com/account/data-privacy) says inference data is not used for training, inputs and outputs are normally deleted after processing, and operational metadata is retained. It reserves exceptions for request logging needed for debugging or security. Accepting that documented policy is distinct from obtaining a strict zero-retention agreement. The adapter opts into no batch processing, webhooks or explicit prompt-retention setting. DeepInfra's [automatic, best-effort prompt caching](https://docs.deepinfra.com/chat/prompt-cache-retention) is separate from optional explicit retention controls; omitting a retention field does not prove all caching is disabled. Local Project Room evidence is retained independently under your private controller home.

## Setup

```sh
python3 project_room.py setup --deepseek-config /absolute/private/path/to/deepseek-provider.json --delegate-provider deepseek
```

`--deepseek-config` must be an absolute path to a private, key-free provider configuration (see the next two sections); setup loads and validates it with the same validator the adapter itself uses at every launch, and never reads a key or touches the network. `--delegate-provider` accepts `deepseek`, `qwen`, or `none`, and the selection rules are deliberately compatible with the pre-DeepSeek flows:

- A provider chosen with `--delegate-provider` is recorded in `config.json` as a deliberate selection and stays in force until another explicit `--delegate-provider` replaces it, even when a later run merely supplies a `--qwen-config` or `--deepseek-config` (the file is stored, the selection is not switched).
- With no recorded selection, the legacy inference applies at every read: `qwen` when a `qwen_config` is configured, else `none`. A plain `setup` followed by `setup --qwen-config ...` therefore enables Qwen for new rooms exactly as it always did; an inferred default is never written down as if it were a choice (`doctor` reports `delegate_provider_selected`).
- Selecting DeepSeek is always explicit. Supplying `--deepseek-config` when no selection is recorded is refused before anything is written, with the instruction to pass `--delegate-provider deepseek` (or `qwen`/`none` to keep the file stored but unselected), so a DeepSeek configuration is never reported as configured while no room could use it.
- Selecting `deepseek` requires a `deepseek_config` (now or previously supplied); selecting `qwen` requires a `qwen_config`.
- Only a configuration supplied in the same run, or a provider explicitly reselected in it, is validated. A stored provider file that is missing or on an unmounted volume never blocks an unrelated change such as `--claude-bin`; reselecting that provider, or supplying the file again, validates it and reports `config_missing`. Stored settings are never cleared silently.

Running this command again never changes a room opened earlier — see [Original-room ownership](#original-room-ownership).

## Enter the key

```sh
python3 deepseek_adapter.py set-key --home ~/.project-room --backend deepinfra
```

`set-key` runs only at an interactive terminal (it checks the process is attached to a TTY and refuses otherwise), reads the key twice with `getpass` so it is never echoed or captured by shell history, and refuses on a mismatch between the two entries. Before it asks for anything, it walks the key path from the filesystem root with the same owned, symlink-refusing traversal that guards every read (next paragraph): a symlinked, foreign-owned, or group/other-writable ancestor is refused as `key_unsafe_ancestor` before any secret is requested, each missing directory on the way is created `0700` relative to the previous descriptor, and an existing key directory whose permissions have been loosened is refused rather than repaired. It then writes the key as a `0600` file through an exclusive temporary file plus rename, so a partially written key is never visible at the final path, and refuses to replace an existing key unless `--rotate` is passed (a symlink or any other non-regular entry at the key path is refused outright, never rewritten through). `--backend deepinfra` selects its separate key file and hidden prompt; `--backend official` (or omitting the flag) selects the historical official key file. Alternatively, use `--config /absolute/private/path/to/provider.json` for that configuration's backend and key path. The selectors are mutually exclusive. A DeepInfra configuration must include `backend: "deepinfra"` even when used only for key entry. An already valid key file does not need to be re-entered.

The key is read at exactly two moments: inside the detached worker when a job's request is sent, and by the explicit `probe` command when it sends its one synthetic request — never at submit, status, result, or health time — and `DEEPSEEK_API_KEY` in the environment is ignored entirely. The key file's directory is reached by walking every ancestor from the filesystem root with `O_NOFOLLOW`: a symlinked ancestor, an ancestor owned by anyone other than root or the current user, or an ancestor writable by group/other without the sticky bit is refused as `key_unsafe_ancestor`; the immediate key directory itself must be user-owned with no group/other permission bits at all. The key file must then be a user-owned regular file, mode `0600`, at most 4,097 bytes, containing exactly one printable ASCII token (a single trailing newline is stripped). `deepseek_health` and `doctor` report only key-file metadata — `present`, `ok`, and a reason code among `key_missing`, `key_unsafe_mode`, `key_unsafe_ancestor`, `key_foreign_owner`, `key_oversized`, `key_not_regular`, `key_empty` — nothing ever reads or prints the key's contents for diagnostics.

## Provider configuration and its validator

The [official example](../examples/deepseek-provider.example.json) and [DeepInfra example](../examples/deepinfra-provider.example.json) show each complete profile. The following table preserves official compatibility defaults; DeepInfra replaces the backend, URL, model, key filename, output cap, context evidence basis and request timeout as listed above. All other defaults and validation bounds are shared. The key-free rule is a schema rule: unknown fields are refused, any field whose name contains `key` other than `api_key_file` is refused, and `api_key_file` must be an absolute path, so the configuration has no field in which a credential value belongs and the adapter never writes one into it. The validator does not scan the remaining string values for secrets; the file is expected to stay private under the controller home, and its exact bytes are pinned by digest into every room that snapshots it.

| Field | Default | Notes |
| --- | --- | --- |
| `backend` | `official` | One of the two fixed transports above; old configurations without the field remain official. |
| `base_url` | `https://api.deepseek.com` | Must exactly match the selected backend; a URL alone never changes transport. |
| `model` | `deepseek-v4.1-flash-expires-on-0910` | An exact, printable model identifier; the adapter refuses any other observed `model` value mid-stream (`model_mismatch`). |
| `api_key_file` | `null` → `<home>/secrets/deepseek-api-key` | Absolute path only; never a credential value itself. |
| `reasoning_effort` | `max` | Deep-lane thinking effort; one of `low`/`high`/`max`. |
| `max_tokens` | `393216` | Pinned deep-lane output budget. |
| `context_tokens` | `1048576` | Provisional context size (`context_basis: provisional_v4_family`); not a verified capacity claim. |
| `ask_max_tokens` | `8192` | Pinned `deepseek_ask` output budget. |
| `ask_effort` | `low` | Default `deepseek_ask` effort; one of `none`/`low`. |
| `max_input_bytes` | `614400` | Framed-input ceiling; requests over this are refused, never truncated. |
| `min_tokens_per_second` | `40` | A disclosed sizing assumption for the timeout below, not measured throughput. |
| `connect_margin_seconds` | `60` | Added on top of the sizing-derived timeout. |
| `request_timeout_seconds` | `9891` | `= ceil(max_tokens / min_tokens_per_second) + connect_margin_seconds`; a sizing assumption, not a measurement or an ETA. |
| `read_idle_seconds` | `120` | Longest gap between stream reads before `read_idle_timeout`. |
| `max_concurrent_per_room` | `1` | Local admission bound; the deep and ask lanes share the same room slot. |
| `max_concurrent_per_host` | `2` | Local admission bound across every room under the same controller `home`. |
| `max_context_files` | `16` | Most `context_path` files per request. |
| `max_context_file_bytes` | `262144` | Most bytes per `context_path` file. |
| `max_content_bytes` | `8388608` | Retained answer-content cap. |
| `max_reasoning_bytes` | `8388608` | Retained reasoning cap (never exposed by any tool). |
| `max_wire_bytes` | `134217728` | Total SSE bytes accepted before the stream is capped locally. |
| `max_wire_tail_bytes` | `65536` | Size of the redacted diagnostic wire tail kept per job. |
| `max_metadata_bytes` | `1048576` | Per-job metadata budget: the wire tail, a 64 KiB reserve derived from the encoded-record bounds (24 KiB `request.json`, 8 KiB `meta.json`, 24 KiB `resolution.json`, 8 KiB for `heartbeat.json`/`cancel.json` and one in-flight atomic temporary), and the remainder as the `worker.log` bound. |
| `max_sse_line_bytes` | `1048576` | Longest single SSE line accepted. |
| `max_retained_bytes` | `1073741824` | Host-wide retention quota across every job's evidence. |
| `max_jobs` | `10000` | Ledger row cap; evidence is never deleted automatically. |

The validator (run at `setup`, again when a room snapshots the configuration, and again every time the adapter starts) also requires: `max_wire_bytes >= max_tokens*320+1048576`; `max_content_bytes` and `max_reasoning_bytes` each `>= max_tokens*8`; `request_timeout_seconds >= ceil(max_tokens/min_tokens_per_second)+connect_margin_seconds`; `read_idle_seconds < request_timeout_seconds`; `max_wire_tail_bytes + 65536 <= max_metadata_bytes` (the 64 KiB reserve is the sum of the bounds enforced on each record's encoded JSON bytes: 24 KiB `request.json`, 8 KiB `meta.json` with usage counters accepted only up to 2^53-1, 24 KiB `resolution.json`, 8 KiB for `heartbeat.json`/`cancel.json`; whatever remains of `max_metadata_bytes` after the wire tail and that reserve is the bound on the private `worker.log`, reported by `deepseek_health` as `bounds.worker_log_bytes`, 917,504 bytes by default); `max_sse_line_bytes <= max_wire_bytes`; `context_tokens > max_tokens`; `max_input_bytes <= context_tokens - max_tokens` (one byte per token, conservatively — no tokenizer is bundled and no exact token count is claimed); `max_context_file_bytes <= max_input_bytes`; `ask_max_tokens <= max_tokens`; `max_concurrent_per_host >= max_concurrent_per_room`; and that one worst-case job's reservation (`max_input_bytes+max_content_bytes+max_reasoning_bytes+max_metadata_bytes`, which excludes unretained wire bytes) fits within `max_retained_bytes` — a sanity bound on the quota itself, separate from the live sum checked at every admission.

## Tools, lanes, and context

The adapter exposes a separate tool catalog from the 21 unchanged `room_*` tools:

| Tool | Purpose |
| --- | --- |
| `deepseek_submit(task, context?, context_path?, request_id, diagnosis?)` | Submit one self-contained deep task. Deep lane always: thinking enabled, the configured `reasoning_effort` (default `max`), the pinned `max_tokens`; the schema carries no `effort`/`max_tokens` fields, so no tool call can lower them. Returns a durable `job_id`. |
| `deepseek_ask(question, context?, request_id, effort?, diagnosis?)` | A quick question on the same durable job machinery with a small output budget (`ask_max_tokens`) and `effort` `none` (thinking disabled) or `low` (thinking enabled, `reasoning_effort: low`); waits inline up to 45 seconds and returns the answer when it completes in that window, otherwise the job to wait on. |
| `deepseek_status(job_id, wait=true, timeout_s<=49)` | Wait (up to 49 seconds, default 45) and read allowlisted ledger facts. `wait=true` is required; chain bounded waits instead of polling. |
| `deepseek_result(job_id, offset=0, max_chars<=32768)` | Read a bounded chunk of a completed job's answer, with `next_offset`, `total_chars`, `content_sha256`, and `content_path` (the export artifact; `null` with `export_reason` when export publication failed safely — chunks are still served from the single private copy). |
| `deepseek_cancel(job_id)` | Ask the owning worker to close its connection. The provider may still finish and bill; the job records `abandoned_cancelled` with `remote_outcome: unknown`, never a claimed remote cancellation. |
| `deepseek_health()` | Read configuration, integrity, key-file metadata (never contents), export-directory diagnostics, storage, admission counts, room-stop state with the resolve command, and the latest probe receipt. No network call. |

Both request bodies carry `model`, `messages` (fixed system framing plus the user turn), `stream: true` and `max_tokens`. Official requests retain their `thinking` object and `reasoning_effort` when enabled. DeepInfra sends no `thinking` object: `reasoning_effort` carries the pinned deep effort, `low` for a reasoning-enabled ask, or `none` for a reasoning-disabled ask; `stream_options: {"include_usage": true}` requests streaming usage explicitly. Neither backend receives sampling overrides, tools, batch, webhook or explicit prompt-retention fields. DeepInfra's `reasoning` and `reasoning_content` deltas are retained separately from answer content with the same bounds and private-artifact rules.

Usage numbers come from the final content chunk or a usage-only chunk and only under the recognized counter names (`prompt_tokens`, `completion_tokens`, `total_tokens`, `prompt_cache_hit_tokens`, `prompt_cache_miss_tokens`, and the `cached_tokens`/`reasoning_tokens` detail fields); missing usage is reported as `null` with `usage_source: missing`, and usage that arrived without any recognized counter is `null` with `usage_source: unrecognized` — never coerced to zero either way.

`context_path` names one or more absolute files lexically beneath the verified worktree the controller passes as `PROJECT_ROOM_WORKTREE`; it is refused outright when that variable is absent. Entries may not be dotfiles, and may not match a credential-looking name (`*.key`, `*.pem`, `id_rsa`/`id_ed25519`, `credentials*`, etc.); each must use an allowlisted source/doc/build suffix or a small set of common bare file names (`Makefile`, `Dockerfile`, `LICENSE`, and similar). At most 16 files of 262,144 bytes each are read, through descriptor-relative opens that never follow a symlink. Total input bytes (fixed framing plus task plus inline context plus every named file) over `max_input_bytes` are refused explicitly with the current estimate; nothing is ever silently truncated.

`request_id` must match `[A-Za-z0-9._-]{1,200}`. The identical `request_id` with the identical payload returns the existing job (idempotent, safe to retry the tool call itself); the identical `request_id` with a different payload is refused (`request_id_conflict`); an identical payload under a brand-new `request_id` is refused (`duplicate_payload`) unless the prior job ended `not_started` (always permitted) or `rejected_before_generation` (permitted only with a nonempty `diagnosis` recorded on the new job) — this is what stops accidentally paying twice for the same request.

## Durable jobs and the ledger

Every job is a durable row in `<home>/deepseek/ledger.sqlite3` (`synchronous=FULL`, `BEGIN IMMEDIATE` transactions, `UNIQUE(room_id, request_id)`) plus a private `0700` directory at `<home>/deepseek/jobs/<job-id>/` holding `request-text` (the admitted task text as the exact UTF-8 bytes that were measured against `max_input_bytes`, never JSON-escaped, so NUL, newline, quote or backslash-heavy input cannot inflate what is retained), `request.json` (the metadata record: parameters, digests, sizes, context-file digests, an optional diagnosis of at most 4,096 bytes; refused at admission as `request_metadata_too_large` when its encoded JSON would exceed 24 KiB, since escaping expands control characters, rather than truncated), `content`, `reasoning`, `meta.json`, a redacted 64 KiB `wire-tail`, `worker.lock`, `heartbeat.json`, a `worker.log` bounded to its share of `max_metadata_bytes` (the detached worker routes its own stdout/stderr through a byte-bounded sink that drops further output after one truncation marker, so a chatty or crashing worker cannot grow the log past the reservation), and (once resolved) `resolution.json` (its encoded record bounded at 24 KiB) — every file `0600`. Admission commits the durable ledger row (which owns the job directory and reserves the worst case) with the lease already held and *before* `request-text`/`request.json` are written, so a crash at any point leaves no unowned bytes: a row that never got its request files is relabelled `not_started` after the startup grace with its bytes measured, a storage failure while writing them is `request_write_failed` (proven unsent), and the worker reads both files back and cross-checks size and digest before anything can be sent. The payload digest that drives idempotency and admission excludes `request_id` itself and covers the room, the profile digest (adapter source plus configuration), the lane, model/effort/output settings, the exact task/context bytes, every context file's digest, and the worktree identity, so `request_id` is purely a client-chosen idempotency key, not part of what is deduplicated.

The worker loads the admitted request through exactly one path: it reads `request.json` within its 24 KiB bound and `request-text` within `max_input_bytes`, and requires the text's size and SHA-256 to match the record; any inconsistency is a proven-unsent `not_started`/`request_unreadable`, never a silently truncated or repaired request. The reservation charged at admission (`max_input_bytes + max_content_bytes + max_reasoning_bytes + max_metadata_bytes`) therefore covers every file the job can retain.

The exact job lease (`worker.lock`, `flock`) is acquired inside the same admission transaction that publishes the `queued` row, before that row is visible, and is handed to the detached worker through `pass_fds`; the worker re-validates the inherited descriptor (same inode, a regular user-owned file) before it will run anything on it. A status read never probes a job's lease until it is at least 10 seconds old, so a slow-to-start worker is never mistaken for one that vanished — the same fix applied to the general job supervisor in `project_room.py`; see [recovery](recovery.md).

The adapter opens exactly one verifying TLS 1.2+ connection to the configured fixed host (`api.deepseek.com` or `api.deepinfra.com`) per request, follows no redirect (every `3xx` is refused outright as `failed_after_send`), and uses no proxy; the only non-production transport is an in-process fake loopback connection that the test suite injects by replacing the HTTPS connection class directly, never through configuration, the CLI, or MCP. Cancellation and the local deadline are both observed only between stream reads, so a completely silent stream can defer either by up to `read_idle_seconds` (120 seconds by default).

## Provider availability, tool discovery, and inference are different checks

- A successful `deepseek` MCP `initialize`/`tools/list` proves only that the adapter process started and its own provider-inventory check passed (or was skipped, when invoked without `--room-root`); it makes no network call.
- `deepseek_health` (or `deepseek_adapter.py health`) reads configuration, integrity, key-file metadata, storage, and admission counts; it also makes no network call, so it cannot prove the endpoint or key are currently accepted.
- `deepseek_adapter.py probe --home HOME --room ROOM_ID --room-root HOME/rooms/ROOM_ID --config HOME/rooms/ROOM_ID/profiles/deepseek.json` (the `--config` value must be the absolute path of the room's pinned snapshot; a relative path such as `profiles/deepseek.json` is refused with `config_invalid`) sends exactly one tiny paid synthetic request with the pinned deep settings and proves the endpoint, key, and accepted parameters for that one request only — never capacity, throughput, or quality. It is an explicit, deliberate CLI action: never automatic, never an MCP tool, and not tied to an interactive terminal, so authorized automation (Astra, after independent acceptance and installation) runs it as well as the user; only `set-key` and `resolve` require the user's own terminal. It is the one key read outside a worker. With `--room-root` it refuses (`inventory_mismatch`, exit 2, no request) when the room's pinned adapter/config digests do not match, and it writes a credential-free receipt to `<home>/deepseek/probes/` that `deepseek_health` and `doctor` summarize as `latest_probe`; when that directory holds more entries than the bounded scan reads (4,096), `latest_probe` reports `unavailable_reason: probe_directory_exceeds_bound` rather than presenting a possibly stale receipt as the latest one, because nothing prunes receipts automatically. A receipt is `completed` only when the stream identified the exact configured model; a stream that never names its model ends `failed_after_send`/`model_unverified` with `observed_model: null`. Astra runs live probes outside tests; the automated suite never touches the network.
- A completed `deepseek_submit`/`deepseek_ask` job proves inference succeeded for that exact request. It does not independently prove task correctness — Sonnet still verifies returned code against current anchors before applying it, the same as any other delegate.

## Preview model expiry and unavailability

The historical official default model name states its own expiration (`deepseek-v4.1-flash-expires-on-0910`), and both it and the 1,048,576-token `context_tokens` figure are provisional, user-authorized facts carried into the configuration, not an independently verified DeepSeek-V4.1 capacity claim. When the provider reports the model, key, or request unavailable, the adapter records an explicit availability code and a terminal state; it never silently retries against a different model or endpoint. Only a definite pre-generation refusal becomes `rejected_before_generation` (not billed): an HTTP status in the diagnosed set 400, 401, 402, 403, 404, 405, 413, 414, 415, 422, 429, 431 (DeepSeek documents 400/401/402/422/429 as request refusals; the others are HTTP-level refusals of the request itself) together with a validated JSON error envelope, with `availability` set to `credential_rejected` (401), `insufficient_balance` (402), `model_unavailable` (404), `provider_unavailable` (429), or `request_rejected` (the rest). Any other 4xx — for example 408 request timeout or 409 conflict — is `failed_after_send` with error code `http_NNN_ambiguous` and `availability: outcome_ambiguous` even when its envelope validates, because a valid envelope does not prove generation never started. Any 5xx response — with or without a parseable envelope — and any 4xx response without a validated envelope are also `failed_after_send`. Every `failed_after_send` outcome stops the room's DeepSeek lane, because the request reached the provider and its outcome cannot be trusted. The envelope's `type`/`code` is recorded only as a classification (`error_type`) from a fixed vocabulary such as `invalid_request_error`, `authentication_error`, `insufficient_balance`, `rate_limit_error`, `server_error`, or `unrecognized` — never the provider's own string. Per the pinned delegation policy, Fable itself never substitutes another model silently: when DeepSeek is unavailable or rejects the pinned parameters, Fable reports the failure and routes the task to an appropriate Claude tier, recording the reason in its routing log.

## Routing calibration after install

Installing the adapter and selecting `--delegate-provider deepseek` only proves configuration was accepted; it does not prove the endpoint, key, or model actually work end to end (see the previous two sections). The agreed order after Astra's independent acceptance and the normal plugin install is:

For a backend change, perform the separately authorized synthetic probe first. The additional calibration tasks below are separate work, not automatic extra requests caused by changing configuration. Earlier official-backend calibration is not evidence of hosted-model quality.

1. **Live probe (Astra).** Astra runs `deepseek_adapter.py probe` with the pinned deep settings against the installed adapter and keeps the credential-free receipt. This verifies endpoint, key, and accepted parameters for that one request.
2. **Two bounded deep calibration tasks (assigned by Fable).** Open one fresh feature room dedicated to calibration (`room_open` with an obviously throwaway feature name, created after setup selected DeepSeek so it snapshots the DeepSeek profile; never this repository's bootstrap room) and hand off. Fable assigns exactly two `deepseek_submit` deep-lane tasks, each self-contained and sized to complete inside the remaining attempt window: (a) an implementation task judged against independently prepared binary-edit edge-case tests that run as the handoff's own gates, so DeepSeek's code is checked by executable evidence rather than by its own claims; and (b) a review task over a synthetic provider-job module carrying five seeded faults (identity, retry, concurrency, truncation, credential), judged by how many of the five the review actually finds and whether it invents others. A `deepseek_ask` question is not a substitute for either task.
3. **Actual Read-access proof.** Before either result is relied on, Fable (or the Sonnet worker applying it) reads the exported `<home>/deepseek/exports/<room-id>/<job-id>.md` file with the `Read` tool under the profile's granted `--add-dir` and validates its `content_sha256` against `deepseek_result`. Configuration presence is not proof: a room whose export directory was recreated after being merely missing, or whose publication failed safely (`content_path: null` with an `export_reason`), still serves chunks through `deepseek_result` but not through a direct file read. If the read is denied, stop that dependent calibration step, diagnose the permission grant, and neither treat the answer as read nor broaden the directory grant silently.
4. **Adjudication and acceptance.** Fable checks the evidence and any fixes it had to make (recording each route, the observed model, usage from the ledger, and the job ids in its routing log) and gives the engineering verdict; Astra independently checks the product outcome. These are narrow calibration facts for that install and that room's settings only; they do not certify quality, throughput, or that a differently configured room will behave the same, and they do not change the pinned deep settings.

## Multi-room concurrency bounds

Admission is local to the controller `home`, not global to the provider account. `max_concurrent_per_room` (default 1) admits at most one queued-or-active job — deep or ask, they share the same room slot — per room at a time; a second submission is refused as `busy` until the first reaches a terminal state. `max_concurrent_per_host` (default 2) admits at most that many active jobs across every room sharing the same controller `home`, regardless of which rooms they belong to. Both bounds, plus the storage reservation (`max_retained_bytes`) and job-count (`max_jobs`) limits, are local owned-execution bounds only: a request abandoned locally (a local deadline or `deepseek_cancel`) may still be running and billing remotely, and none of these counters reflect the provider's own account-level concurrency or rate limits.

## Original-room ownership

A room's delegate provider is fixed the moment `room_open` creates it. `project_room.py setup --delegate-provider ...` only changes what a subsequently opened *new* room snapshots; `setup` reports `existing_rooms_unchanged: true`, and there is no command in this version that migrates an existing room's provider, even if its provider later becomes unavailable or a preview model expires. An audited idle-room provider transition is a separately filed proposal, not implemented here; existing rooms keep the exact pinned policy text, MCP server, and (for DeepSeek) provider inventory they were created with.

## The full state table

| State | Meaning | Possibly billed | Stops room / resolve-eligible | Same payload under a new `request_id` |
| --- | --- | --- | --- | --- |
| `not_started` | Proven unsent: spawn failure, cancelled before send, a key problem, a credential found in the assembled payload, the fixed deadline already elapsed before the first byte (`local_deadline_before_send`, checked before and again after connecting), a TCP/TLS connect failure, or a lease-free queued job past the 10-second startup grace. | No | No | Permitted |
| `queued` | Admitted; the worker has not yet reached the send boundary. | No | No | Refused while active |
| `submitting` | Durably recorded (with `fsync`) before any request byte could be sent. | Yes | No | Refused while active |
| `streaming` | Response headers were received; the body is streaming. | Yes | No | Refused while active |
| `completed` | `finish_reason: stop` and `[DONE]` were received and a chunk identified the exact configured model; content was published. | Yes | No | Refused; read the existing job |
| `truncated` | Incomplete output: `finish_reason` `length`/`content_filter`/`other` (any value outside the recognized set is recorded as `other`), or a local content/reasoning/wire cap. Never a completed answer; `deepseek_result` refuses it. | Yes | No | Refused |
| `rejected_before_generation` | A validated JSON error envelope with a status in the definite-rejection set (400, 401, 402, 403, 404, 405, 413, 414, 415, 422, 429, 431), before generation started. | No | No | Permitted only with a nonempty `diagnosis` |
| `failed_after_send` | The request was delivered but its outcome is incomplete, contradictory (including `model_unverified`: no chunk named the exact model), an ambiguous 4xx such as 408/409, or a 5xx server/gateway failure (with or without a validated envelope). | Yes | Yes | Refused |
| `abandoned_local_deadline` | The fixed local `request_timeout_seconds` expired; remote work may continue and bill. | Yes | No | Refused |
| `abandoned_cancelled` | `deepseek_cancel` closed the local connection; the remote outcome is unknown and never claimed as a remote cancellation. | Yes | No | Refused |
| `unknown_delivery` | Delivery is unknown: a send/response transport failure after a possible send, or a worker that vanished after committing `submitting`. | Yes | Yes | Refused |

Only `failed_after_send` and `unknown_delivery` stop a room's DeepSeek lane and are eligible for the resolve procedure below; every other terminal state neither stops the room nor accepts a resolve. The classification is deliberate: any 5xx response — with or without a parseable JSON error body — means the request reached the provider and its outcome cannot be trusted, so it is `failed_after_send`; only a 4xx status from the definite-rejection set whose body validates as an OpenAI-style error envelope (`{"error": {"message": ..., "type or code": ...}}`) is a definite pre-generation rejection (`rejected_before_generation`); a 4xx outside that set (408, 409, and any other status the adapter has not diagnosed as a refusal of the request itself) is `http_NNN_ambiguous`, and a 4xx without a validated envelope is `http_NNN_unvalidated` — both `failed_after_send`, possibly billed, never replayed, because the adapter cannot prove generation never started. The fixed local deadline is enforced at every stage: before connecting, again after connecting, while sending, while waiting for headers, while reading an error body, and between stream reads; it is never reset or extended, and an expiry before the first request byte is a proven-unsent `not_started`.

## Room stop and the user-run resolve procedure

An unresolved `failed_after_send` or `unknown_delivery` job stops new paid jobs in that room only — other rooms are unaffected — and `deepseek_submit`'s refusal carries the exact job and resolve command. Resolving it requires the user, in their own interactive terminal:

```sh
python3 profiles/deepseek_adapter.py resolve --home ~/.project-room --room ROOM_ID --job JOB_ID --note-file /absolute/private/path/to/decision.md
```

`resolve` runs only at a TTY; Astra may prepare the note file and show the exact command, but cannot run it. The note file must contain nonempty text of at most 16 KiB (and at most 24 KiB once JSON-encoded, so a note dense in control characters, quotes or backslashes is refused as `note_too_large` before anything is recorded) recording the user's actual decision, acknowledging the unknown remote outcome and possible billing. Resolving inserts one idempotent resolution record (a second `resolve` on the same job returns `duplicate` with no change), writes `resolution.json`, and lifts only that one job's stop: it changes no terminal state, resends nothing, and deletes nothing. The identical payload stays deduplicated, and any other unresolved eligible job still stops the room. `resolve` refuses a job in any other state. There is no `room_*` MCP tool for this; it cannot be run by Astra or Fable on the user's behalf.

## Export folder semantics

A completed job's content is published into `<home>/deepseek/exports/<room-id>/<job-id>.md` as a `0400` file, created `0700` on demand, in an order that keeps exactly one authoritative, retrievable copy at every failure and crash boundary: the export name is hard-linked to the private `content` inode (same filesystem, no symlink ever followed, no bytes duplicated), the inode is fixed to `0400`, and the export directory is `fsync`ed — only then is the private name removed. Any failure before the export is durable (the link, the mode change, or the directory `fsync`) rolls the export name back, restores the private copy's mode, and reports `content_path: null` with `export_reason: export_unavailable`; the private copy in the job directory stays authoritative and `deepseek_result` serves chunks from it. Once the export is durable it is authoritative; a failure to remove the private name afterwards leaves a stale hard link that shares the inode (nothing is duplicated, and accounting counts it conservatively), and a stale private name is never recorded as a second content path. A different artifact already at the export name yields `export_conflict` and is never overwritten; an identical one (same digest) is adopted. A worker that dies between publication and its ledger commit leaves the job `unknown_delivery` with that single durable copy on disk for inspection; the relabel counts the export's bytes against retention (an artifact under the job's name in the room export directory, reached through owned descriptors, never followed through a symlink), but it is not retrievable through `deepseek_result` and nothing adopts it automatically. An existing artifact at the export name that cannot be read and verified identical is `export_conflict`, never overwritten. `content_sha256` is recorded and re-validated on every `deepseek_result` read; a changed artifact yields `content_changed` and refuses to serve it. Mode `0400` exists to prevent an accidental overwrite by this same local user, not as a sandbox against a hostile process running as that same user. A merely missing export directory is recreated automatically (at most the three levels `deepseek/exports/<room-id>` below the existing controller home, each reached and created relative to the previous directory descriptor so no ancestor symlink is ever followed); anything else about it (wrong owner, wrong type, unsafe mode) refuses instead of being repaired: the launch gate, the adapter's own publication step and the directory creator at room setup all refuse group/other permission bits (the remedy is `chmod 700`), so an unsafe directory is named at room creation rather than discovered at launch. See [Routing calibration after install](#routing-calibration-after-install) for verifying the export file is actually reachable through `Read`, not merely present on disk.

## Attempt timeout interaction

The Claude invocation timeout pinned into a room's implementation profile (`implementation_timeout_seconds`, default 3600 seconds) is unchanged by this version and still ends Fable's attempt at `attempt_deadline_at`. A DeepSeek job is a separate detached process with its own `request_timeout_seconds` (9,891 seconds by default) and can keep running, and be billed, after Fable's attempt itself ends. A later authorized attempt on the same handoff (a correction, or an audited recovery successor) can read that saved job by its `request_id` or payload digest without resubmitting it, because `deepseek_submit` is exactly-once idempotent per room/request_id. Fable's implementation packet carries `implementation_timeout_seconds`, `attempt_started_at`, `attempt_deadline_at`, `delegate_provider`, `delegate_export_dir`, and a `timeout_note` so it can size deep tasks to the remaining window rather than start one it cannot itself wait out.

The interrupted-implementation recovery lane (see [recovery](recovery.md)) still requires its own host-boot boundary before a successor may launch; a restart that satisfies that boundary also kills any local worker that was still streaming a DeepSeek response, leaving that request's remote delivery unknown. That job then ends `unknown_delivery` (or `failed_after_send` if the failure was already observed) and stops the room's DeepSeek lane exactly like any other unresolved delivery failure — see [Room stop and the user-run resolve procedure](#room-stop-and-the-user-run-resolve-procedure) above.

## Transcript audit

```sh
python3 project_room.py transcript-audit --room ROOM_ID --handoff HANDOFF_ID --attempt N
```

(equivalently `python3 transcript_audit.py --home HOME --room ROOM_ID --handoff HANDOFF_ID --attempt N`.) This is CLI-only and read-only; there is no `room_*` MCP tool for it, and neither form creates a controller home or opens the registry for writing (a mistyped `--home` reports the missing registry and provisions nothing). It derives the session UUID, transcript root, and the attempt's time interval from the immutable handoff manifest, the pinned configuration, and that attempt's own process receipts, accepting no override of any of those. It streams the entire exact parent transcript and every bounded `agent-*.jsonl` file in the session's subagents directory through owned, symlink-refusing descriptors, and reports SHA-256 digests, bytes scanned, record counts, and tool-use counts for `mcp__qwen-local__*`, `mcp__deepseek__*`, `Agent`, and `Task` — both for the whole file and restricted to the attempt's own interval — plus `launched_children` (launched by the parent), `requested_descendants` (launched from any scanned file: a grandchild launched by a child counts too), attributable/unattributed child counts (a child is attributable when the parent or any scanned descendant launched it), `children_missing`, per-launch evidence counts (`launches`, `unresolved_launches`, `unidentified_launches`, `failed_launches`), `children_listing_complete` (every `agent-*.jsonl` the session's subagents directory holds was read, whether or not a receipt attributes it), an `attribution` block (records carrying another session id, duplicate record uuids and inline sidechain copies are counted and reported there, never subtracted, with `ambiguous: true` when any occur), and a `complete`/`reasons` verdict. Completeness requires that every `Agent`/`Task` tool use carries launch evidence in its own file (a result naming the child agent, or an error result proving no child started; a tool use with no result at all is `launch_evidence_missing`, and one whose result names no child is `launch_unidentified`, which is how child transcripts record their own launches, so a session in which a child launched further agents cannot be certified complete even though every listed child file was read), that every requested descendant has a scanned transcript, and that the whole observed subtree stayed stable: the parent, every earlier child, and the bounded directory listing are re-checked after the last file is read, so a parent or child that grew while later files were being scanned, or a child file that appeared or disappeared mid-scan, is incomplete (`parent_changed_during_scan`, `child_changed_during_scan`, `children_dir_changed`). Other reason codes include `source_growing`, `malformed_records`, `overlong_records`, `transcript_oversized`, `child_missing`, `children_truncated`, the attempt-receipt codes, and transcript-location codes such as `transcript_unparsable` or `transcript_missing_or_ambiguous`. Attribution is reported separately from completeness and never hides scanned tool use: a Qwen call in any scanned file counts, attributable or not. It emits no text or tool arguments. It exits `0` when `complete` is true, `1` when the scan finished but is incomplete, and `2` for unusable identifiers.

Because it counts tool uses rather than trusting a report's own claims, it is the recommended way to corroborate a report's routing claims — including confirming that a legacy Qwen room's report of no Qwen use is actually true: absence of Qwen is acceptable evidence only when the audit's `complete` is `true` and every Qwen count is zero.

## Privacy guarantees

Reasoning is written to a private per-job artifact (`reasoning`, capped by `max_reasoning_bytes`) so caps and diagnostics can account for it, but no tool ever returns it: `deepseek_result` serves only `content`, and `deepseek_status`/`deepseek_health` never read it. The key is entered only at an interactive terminal with `set-key` (which refuses an unsafe ancestor before asking for it), is read only inside the detached worker at the moment of the request and by the explicit `probe` command, is never accepted from the `DEEPSEEK_API_KEY` environment variable, is redacted from the private wire-tail diagnostic (the retained window is redacted first and bounded afterwards, so replacement can never grow the tail past `max_wire_tail_bytes`, and a key fragment cut by the window's edge is dropped too), and is checked against the raw request text and the assembled request body before sending — a request whose text happens to contain the exact key value is refused as `not_started`/`credential_in_payload` rather than sent. No status, health, probe, or log surface ever prints the key's contents; `key_file` diagnostics are metadata only. No provider-derived string reaches a public outcome, the ledger, `meta.json`, a probe receipt, or `worker.log`: `error_type` is a classification from a fixed vocabulary or `unrecognized`, `observed_model` is either the exact configured model or `null` (a differing model is reported as `model_mismatch`, an absent one as `model_unverified`, and the observed value is never inferred from the request), `finish_reason` outside the recognized set is `other`, and usage counters outside the recognized names, or beyond the exact-integer range (2^53-1), are dropped; counters already captured are never erased by a later empty or unrecognized usage object. As a final backstop, any outcome field that still contains the exact key value is replaced with `[REDACTED]` before it is stored. The provider's own bytes survive only in the private, key-redacted `wire-tail` (the last 64 KiB of a stream, or of a non-200 error body), which no tool returns. Every ledger row, job artifact, probe receipt, and export lives under the controller's private `home` directory (`~/.project-room` or `PROJECT_ROOM_HOME`), reached only through owned, symlink-refusing directory descriptors.

## Honest limits

DeepSeek is a text delegate, not an agentic runtime: it returns proposed code, tests, reviews, and reasoning summaries, and never executes anything, edits a file, or invokes a tool itself — Sonnet applies and verifies exactly as it already does for Qwen's output. The historical official default model name states its own expiration, and both it and the 1,048,576-token `context_tokens` figure are provisional, user-authorized facts carried into the configuration, not a verified DeepSeek-V4.1 capacity claim; no tokenizer is bundled, so `max_input_bytes` is enforced at one conservative byte per token rather than an exact count. `request_timeout_seconds` is a disclosed sizing assumption, not a measured throughput figure or an ETA. Local admission bounds reflect only what this controller will launch locally; they say nothing about the provider's own account-level limits, and a locally abandoned request may still run and bill remotely. A probe proves only that one tiny request succeeded with the pinned parameters at that moment — never capacity, throughput, or output quality; live probes run outside the automated test suite, which uses a fake in-process loopback connection and synthetic keys and never touches the network. Redaction of the private wire tail matches the exact configured key bytes; a provider that echoed a transformed form of the key could not be caught by it, which is why no provider-derived string is ever copied into a public field in the first place. This documentation and the adapter make no claim about DeepSeek's pricing, promotional terms, the expiry timezone encoded in the model name, or output quality.
